# SDK callback producer transport

`scripts/trial_sdk_producer_driver.py` services one independent direct child for
one full callback. It creates a fresh `NativeProcessOwner` before launch. The
authorized fixed builder launches and contains that child separately; the
transport has no command factory or runtime admission operation. It does not
use `SDKDirectWriter` and cannot add SDK initialization, users or replies.

Construction borrows the exact `StreamEvent`/`Callback` handoff and its original
first-read interval, request hash and five-second deadline. These Python types
and references assume trusted serialized access. Reconstructed objects or
matching payload fields do not authenticate an invocation. A session coordinator
must keep one original active producer and prevent callback reuse.

## Full input and actual progress

`Callback.iter_input_json()` supplies full canonical semantic JSON, including
unrecognized input fields. The driver never uses the marker projection or joins
the whole body. One yielded chunk of at most 8192 bytes stays held with its
offset; actual readonly offers are at most 512 bytes. The encoder also retains
scratch while suspended. This is not a 512-byte total memory claim. Decoded
graphs and Unicode encoder tokens remain under the aggregate attempt controls.

Generated bytes/hash and actual positive-write bytes/hash are separate. Each
returned positive write is recorded before a later clock check can refuse.
Would-block reports no accepted bytes. A write that takes effect then raises
has an unknown outcome: the driver retains the original native input owner's
`write_unknown` independently of returned-positive counts. Hash interruptions
retain explicit unknown flags rather than claiming a matching count/hash pair.

After true iterator exhaustion, the generated and actual-written counts and
hashes must all match the held callback input. Only then does the driver attempt
producer stdin EOF once. A temporarily empty chunk is not exhaustion. No LF or
wrapper is added. This finite producer stream is distinct from continuing SDK
stdin and its result-to-EOF policy. `NativeInput` limits each offer, not cumulative
producer input; the unchanged 8500-byte SDK protocol limit belongs to the
controller and its sole SDK writer.

## Output, wait and failure

Two separate 512-byte slabs drain stdout and stderr while input progresses.
Actual positive read counts/hashes are recorded before clocks, decoding or
policy checks. Stdout uses the existing strict incremental UTF-8 decoder and
JSON parser. The explicit output restriction is one JSON object, or zero bytes
represented by `None`. Trailing whitespace is JSON whitespace; a second object,
invalid UTF-8, duplicate keys and non-object JSON refuse. The driver never
validates an engine's context schema, payload counters or task result.

`take_output()` hands off one parsed graph only after complete verified input,
known stdin close, actual child wait0, both output EOFs, known native-owner
release and another check of the original callback deadline. Taking the graph
twice refuses. A producer error or malformed output yields no usable output
handoff even if it emitted a valid prefix. An empty-output producer still needs
the same observed input, wait and release conditions.

Raw stdout is restricted to 128 KiB and total local output to the original
4-MiB ceiling. These are local upper bounds, not a separate allocation of
attempt capacity. The composition must charge producer input/output together
with native, backend and capture traffic under the original shared stream/raw
queue/resource limits. Stdout decoding, parsed graphs, encoder scratch and
kernel buffering remain separate working allocations. This module establishes
neither composed selected-input charges nor physical-memory fit.

`snapshot()` retains actual input/output progress, unknown flags and the original
owner's PID, launch state, input uncertainty, wait and release. Before EOF a
stream hash describes an observed prefix. Memory-call attempts and batches are
`None`, with measurement explicitly unattested. Seeing no calls in this
transport does not mean the producer made zero calls. Trusted engine/gateway
observations and enforcement before dispatch remain required.

The five seconds start at the incoming callback's conservative read-interval
sample. Construction, launch, encoder completion, producer exit and output
handoff cannot restart that deadline. Final SDK reply serialization and actual
write are still part of it. It is not a measured producer CPU/process elapsed
time or external wall containment proof. The fixed owner must retain its actual
launch/start/end observations separately.

An error poisons the driver, drops its input iterator and decoded graph, preserves
the primary exception and retains iterator cleanup uncertainty. `cancel()` only
drops those local loans. Neither path signals, waits, closes borrowed native
handles or invents successful release. The original `native_owner` remains
available for independent bounded stop/wait/once-cleanup after failure.

## Scheduling and checks

`SDKStreamDriver.step(timeout=.05)` and `SDKSessionDriver.step(timeout=.05)` now
accept a finite poll cap from zero to 50 ms. Defaults retain their previous
behavior; the existing absolute deadline can only shorten the wait. Zero allows
producer and SDK service to alternate without spending 50 ms after every
512-byte producer write. The cap supplies no caller clock or permission.

The fixed combined check alternates both nonblocking steps, waiting 1 ms only
when both are idle. It continues native stderr, wait and pending protocol input
while the independently owned producer runs. This is an ordinary fixture, not
a production session coordinator or native concurrency acceptance.

Run the optional fixed suite only with a fresh absent output directory:

```sh
python3 -B scripts/check_trial_sdk_producer_driver.py --output /absolute/fresh/directory
```

The suite uses guarded readonly authored source snapshots and the existing
owned-group supervisor with ten seconds work, twelve total and 64 KiB retained
output. Eleven standalone cases cover complete 70-KiB Unicode input, concurrently
emitted stdout/stderr, empty output, actual nonzero wait, invalid UTF-8, a second
JSON object, input drift, actual-close/write followed by injected errors, a
post-read clock interruption, a late positive write and interrupted generated
hashing. Count/hash and cleanup uncertainty are checked against actual returned
effects. These cases do not establish full socket saturation or force partial
kernel writes merely by using large input/output.

The combined case runs one SDK-shaped Python surrogate and four independently
owned producer children. Three callbacks carry about 70 KiB; full input counts
and hashes must match. An injected zero-accepted would-block keeps the user
partially written until SessionStart handoff; real writes resume during producer
service. The check requires that progress, native stderr service during a large
callback, actual zero waits/known releases, and four reply-written observations
within their unchanged original intervals. The surrogate receives actual SDK
stdin EOF after its result. Those observations do not prove installed native
behavior, model request delivery or a real memory engine's counters.

## Remaining full-session work

The runtime must select and bind the real producer engine/configuration and
validate its output semantics before passing context to `SDKControl.reply`.
There is no output truncation, success-flag override, fabricated producer wait
or memory-call allowance here. SDK H/E/retention, selected-input and aggregate
stream accounting, actual capture clock/start/T/D and full external-exit/source
custody still need their complete composition. Actual native compatibility,
authenticated origin/witness/model delivery, funded reserved capacity and the
fresh evaluation with both weekly campaigns remain unproved. CAIRN-107 stays
active/HOLD; CAIRN-149/150 remain Done.
