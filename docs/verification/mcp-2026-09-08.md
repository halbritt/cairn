# Native MCP tools and operational note transfer, 2026-09-08

Cairn now exposes search, body/evidence pulls and ordinary capture through a
local stdio MCP facade. It uses the existing Unix API and its authenticated
profile. The [setup guide](../mcp.md) describes its scope and retry behavior.
This implements the accepted design's optional facade without introducing
a separate storage or authority path.

## Actual OpenCode use

A storage note selected and saved by a Codex session in the preceding turn
was retrieved by DeepSeek through OpenCode 1.18.21's native MCP tools. The task
prompt was fixed before invocation: answer the default memory location, home
override and `CAIRN_DATABASE_URL` distinction; inspect the full note, cite its
record ID and distinguish recorded defaults from live deployment state.

Observed sequence:

1. OpenCode discovered and connected to the local Cairn MCP server.
2. The model called `cairn_cairn_search`. The storage note ranked first.
3. It copied that entry's `pull_arguments` into `cairn_cairn_pull`; the returned
   body matched the earlier Codex capture exactly.
4. Its final prose correctly explained all three points, cited the pulled record
   and explicitly declined to treat the note as a current deployment inventory.

The process exited zero after 8.38 seconds. Four relay requests completed with
no relay rejection; three reported usage, while one reported none. The
[metadata](mcp-2026-09-08.json) retains those observations and binary hashes.
Source support was reviewed against the complete pulled body and repository
source, separately from process exit. No strict JSON-format criterion was imposed.

Only search and body-pull tools were permitted; there were no shell, filesystem
or capture tool calls. The child used an isolated home/configuration and an
unusable database address. The parent held the existing provider credential
behind a bounded relay; the child received a disposable relay credential.
The relay and child are terminal, and the temporary home/config were removed.
Raw outputs, operational note bodies and record identifiers remain outside Git.

This is one useful transfer of explicitly curated knowledge between this Codex
session and a different model in OpenCode. It demonstrates native MCP contact
and a completed source-answering task. It does not establish an advantage over
no-memory/direct-context baselines, coding-task improvement, automatic learning,
general recurrence reduction or native Striatum admission. The MCP task was not
linked to a Cairn host-run outcome; that integration remains open. Both sessions
used the existing ordinary profile, so this does not establish independent writer
identities.

## Implementation verification

The SDK client and an independent Python JSON-RPC client both exercise real
PostgreSQL and the Unix API. Coverage includes the exact tool inventory, scoped
capture, A writer stamps, unchanged capture/pull retries, changed-intent refusal,
local-only exclusion from hosted retrieval, mandatory bootstrap, full-body
correspondence, supporting evidence, stale handles, cross-repository refusal,
unknown input-field rejection, output bounds and clean stdio EOF/startup failure.
`make test-integration`, `make check` and module checksum verification pass.

Initial test fixtures exposed three mistaken expectations: Go time values can
represent the same instant with different location objects; an operator who
edits a note cannot independently promote it; and receipt lookup returns
`NOT_FOUND` before checking handles. The fixtures now compare timestamp instants,
edit through the original agent and preserve the existing refusal code. No
store contract was weakened to satisfy them.

The actual model run used the development binary identified in the metadata.
Its successful tool paths were unchanged by the later error-message polish,
which preserves protected-refusal IDs and avoids repeated error-code prefixes.
Deployment of a clean commit is recorded separately.

The implementation decision used Pincite packet `pkt-4bb29d9f02f54170`; full packet,
corpus and retriever identities are in the metadata. Repository precedence,
evidence before intervention, the API ownership boundary and preservation of
existing behavior informed the choice. Eight remaining retrieval obligations are
classified nonmaterial in the local decision record; no broad architecture or
performance acceptance is asserted.
