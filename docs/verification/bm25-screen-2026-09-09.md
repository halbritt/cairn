# Fixed BM25 screening, 2026-09-09

The fixed BM25 candidate produces mixed ranks on the existing public development
workload. It does not earn a production change. Keep lexical v4 and stop tuning
these same questions; revisit with actual long-note failures and relevance labels
fixed before scoring.

## Question and method

Current lexical ranking counts distinct shared terms. A long, mixed-topic note
can therefore match more generic query words than focused guidance. This is a
plausible mechanism, not an established cause of the recent handoff miss: that
miss was repaired by adding missing guidance to the existing note.

The [optional script](../../scripts/compare_bm25_retrieval.py) screens a different
candidate from the earlier inverse-frequency experiment. It uses the term-frequency
saturation and length normalization in
[IR-book equation 86](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html),
with fixed `k1=1.2`, `b=0.75` and `log(N/df)` weights. Those parameters were selected
before scoring and were not tuned afterward. Each query term contributes once.
Document length counts non-stopword token occurrences after underscore expansion;
each original token and its distinct parts count once per occurrence. This explicit
tokenization choice is part of the candidate, not a universal BM25 convention.

Inputs are the unchanged twelve ASCII passages, fifteen answerable questions and
two no-answer controls in the [public workload](../../core/testdata/retrieval-quality.json).
Only `storage?` is a verbatim user question. Other questions and labels are authored
development material already used in prior experiments. The passages contain
19–126 expanded non-stopword tokens; they are not representative long procedures.
The script saves its plan and source hashes before scoring, uses both insertion
orders for recency ties, and excludes zero-score candidates.

## Results

Counts are out of fifteen answerable questions, before eligibility, packing or
delivery. All notes in this comparison have equal assumed scope specificity.

| Method | Insertion order | First | Top three |
| --- | --- | --- | --- |
| Lexical v4 | Forward | 11 | 13 |
| Lexical v4 | Reverse | 10 | 12 |
| BM25 | Forward | 10 | 13 |
| BM25 | Reverse | 10 | 13 |

The aggregate counts conceal tradeoffs:

- Storage location moves from rank 11/4 to 5/5; it still misses the top three.
- Scope broadening moves from rank 1/6 to 3/3, improving one order and worsening
  the other. Original-conflict inspection improves from 1/3 to 1/1.
- Note replacement moves from 2/1 to 2/2.
- `storage?` still returns no results. The unanswered GPU question still returns
  irrelevant candidates; the unanswered price question returns none.

This small improvement in one top-three count, with first-place regressions,
does not establish a generally better ranker. It also does not reject BM25 for
long notes: the hypothesized pressure is poorly represented by this corpus.
No answering-model task, qualitative assessment or sustained benefit comparison
was performed. These rank measurements do not define the project's task-value bar.

## Verification and decision

All 34 baseline query/order results, including complete ranked lists and scores,
match the retained semantic experiment's lexical baseline, which was checked
against real-store v4 results. Candidate vocabulary equals the baseline term set
for every passage. Scores are finite, a second full report is byte-identical,
and reuse of the output directory refuses without changing existing artifacts.
`make check` passed. No store or runtime code changed, so no database, native
harness or deployment tests were repeated.

Run with the standard library, Python 3.11 or later, and a new output directory:

```sh
python3 scripts/compare_bm25_retrieval.py --output /tmp/cairn-bm25-new
```

The [metadata](bm25-screen-2026-09-09.json) retains ranks, exact inputs, parameters,
verification and local evidence pointers. Production scoring and historical replay
remain unchanged. A future corpus-dependent ranker would also need eligibility,
packing and frozen-replay design before integration; this script implements none
of those contracts.
